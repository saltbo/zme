# API contract migration: catalog relationships, charts, torrents, and downloads

The runtime OpenAPI remains 3.1.0. Its contract release is 2.0.0. This is a
coordinated client/server/Agent-skill migration; it does not add a URI version
or an API-Version header. The old routes and response envelopes are removed.

| Previous contract | Replacement |
| --- | --- |
| `/release-candidates`, intermediate `/download-search-results` | `/torrents`: owned, expiring BT resource projections with identity independent of selected media |
| `release-candidates:read`, intermediate `download-search-results:read` | `torrents:read` |
| `/download-sources`, intermediate `/download-links` | `POST /downloads` without `downloaderId`: temporary local delivery; files use `/downloads/{downloadId}/content` |
| local `sourceType`, `uri` | `kind: magnet` or `kind: file`, with `href`; files also have `filename` and `mediaType` |
| `/library` API collection and `/library/resources/{mediaKey}` | `/library/items` and `/library/items/{mediaKey}`; browser page URLs are unchanged |
| `PUT /library/music/favorites` with `selected` | `PUT` or `DELETE /library/music/favorites/tracks/{mediaKey}` |
| `PUT /connectors/{id}/playlists` | `PUT /connectors/{id}/playlist-selection`; GET reads that selection and the update links to its sync job |
| `/…/health-observations` and timestamp items | `GET /…/health`: a fresh current-state read, with `Cache-Control: private, no-store`; no historical observation promise |
| `/connector-login-attempts/{id}/response` with `challenge: poll` | GET the login attempt for progress; the server advances QR login through queued polling |
| form continuation actions | `PUT /connector-login-attempts/{id}/challenge-response` with `input`; accepted responses can be read with GET and identical retries do not resubmit them |
| `/movies/{id}/watch-clickouts`, series equivalent | `/catalog/movies/{id}/watch-links`, series equivalent; `items` contain `provider` and `href` |
| `{item: resource}`, `{job: resource}` | the resource directly |
| provider-specific paginated envelopes | `{items, pagination}`; catalog/chart totals are present only when exact. Finite, unpaged lists use `{items}` |


## Catalog and chart ownership

Content lives under `/catalog`: movies, series, books, albums, independently
identified book/album editions, recordings, people, and genres. The mixed
movie/series query is `GET /catalog/items?q=...&types=movie,series`; returned
summaries point to the canonical content URI and do not have separate result IDs.

| Previous read | Replacement |
| --- | --- |
| `/media-recommendations?kind=...` | `/catalog/movies` or `/catalog/series`, with explicit browse filters |
| `/media-trends`, `/popular-media` | `/charts/{chartId}/entries`; discover the chart definition and periods first |
| `/book-recommendations?mode=subject` | `/catalog/books?subject=...` |
| Book trending | `books-trending` chart |
| `/music` and genre discovery | `/catalog/albums?q=...` or genre/year/type filters |
| Music popular discovery | `album-editions-popular` or `recordings-popular` chart |
| Book and music polymorphic details | Separate work/album, edition, and recording addresses |

Series own seasons; seasons own episodes. Book and album parent collections
list their associated editions, whose `links.self` retain one canonical address.
Album editions own discs and their track positions. A recording can be referenced
from several positions and editions. An album representation embeds an optional
`preferredEdition`; discs belong to that edition rather than to the album itself.
Charts own ranked `{rank, item}` entries and publish their supported periods.

Public catalog query names use `q` and `orderBy`; provider-specific sorting is
translated by the server. Keyword movie/series queries cannot be combined with
browse-only filters. Screen collections and charts use upstream pages of 20.
Catalog/chart totals are omitted when exact counts are unavailable. Existing
library and download pagination retains exact totals.

Torrent queries expose `q`, optional `mediaKey`, `target`, `view`, and pagination.
The server chooses indexer search types/categories and excludes declared non-BT
protocols. First-page results create an owned query snapshot; later pages require
the returned `snapshotId` and reuse the same ordered results. Follow `Link` URLs.
The temporary snapshot is not a public search job. Media/target context is passed
to `GET /torrents/{id}` when preparing an opaque download reference; context never
changes the torrent ID. Both local links and remote downloads use that reference.

Unchanged playlist-selection PUTs reuse the same policy revision and sync job.
Changing the selection away and then back creates a new revision and sync job,
so an old completed job cannot suppress a newly requested synchronization.

## Security and download lifecycle

Downloader reads return safe configuration and configured credential names,
never credential values. Supplying an empty credential patch preserves existing
values. Nested credential/options patches merge; null removes a member or clears
the entire map. Configuration writes remain unavailable to Agents.

Download responses omit upstream source URIs. Public file delivery proxies
torrent bytes without forwarding upstream redirect, cookie, or error bodies.
Local link IDs are encrypted capabilities with a five-minute lifetime and are
redacted in application request logs. This expiry does not expire a magnet URI.
Local handoff does not create a remote task or claim that a local client started
or completed the media transfer.

Both destinations use `POST /downloads` with `resourceRef`. `downloaderId` is
optional: omitting it returns `LocalDownload` (`kind`, `href`, and expiry);
supplying it creates a persisted `RemoteDownload` and requires `Idempotency-Key`.
`GET /downloads/{downloadId}` reads either response through its `links.self`.
The list and task-management operations cover remote downloads; local handoffs
expire automatically. No separate destination object or local task history is added.

`submissionUnknown` records a remote submission whose outcome is uncertain.
ZME recovers only when the adapter supports downstream idempotency, using the
original download ID as its key. ZPan uses its native key. Aria2 uses a stable
GID and can recognize an existing task on a duplicate submission, but its result
[history can be evicted](https://aria2.github.io/manual/en/html/aria2c.html#cmdoption-max-download-result), so ZME does not automatically resubmit an uncertain
Aria2 task. Aria2, qBittorrent, and Transmission remain explicitly uncertain until
the remote client is checked. Recovery also
discovers interrupted submissions from the database.

Task responses expose `monitoringSupported`, `submissionRecoverySupported`,
and `pollingRequired`. Clients stop polling when `pollingRequired` is false.
Submission-only clients are reported as handed off, without invented progress.
Management links appear only for supported task management operations.

## Agent clients and rollout

`media:read` now covers the same movie, series, book, and music catalog reads as
the browser. `library:read` covers the represented user's library and music
collection tracks. Existing ownership checks apply to those reads. An Agent can
obtain an owned track's media key and use `music-track:<mediaKey>` with
`createDownload`, choosing the destination by supplying or omitting `downloaderId`.
The published use-zme skill and helper use the same download contract as the browser.

Before deployment, register the renamed and added scopes at the authorization
server, apply the connector challenge-response and torrent query-snapshot migrations, and ship the server,
SPA, OpenAPI, and skill archive together. Agents must rediscover live operations
and request the new scopes; old grants do not implicitly gain new authority.
Old candidate/search-result references should be replaced with a fresh search. Existing
remote download records and physical search snapshot tables are preserved.
Existing remote music content-key URLs remain supported. Temporary local links
from the old API expire within five minutes and should be recreated after cutover.

Local acceptance uses `pnpm typecheck`, `pnpm lint`, `pnpm lint:arch`, `pnpm test`,
`pnpm test:local-download`, `pnpm e2e`, `pnpm openapi:lint`, `pnpm openapi:diff`,
`pnpm check:skills`, and `pnpm build`. These checks do not deploy the project.
